### Spike Protocol (D-02)

Per CONTEXT.md D-02, budget: half a day (~4 hours) for the full spike including setup, cycle execution, log analysis, and write-up.

**Phase A — Fresh-install baseline (SVR-01/02/03/10/11):**
1. Close SteamVR if running.
2. If this is an UPGRADE from a prior 0.x install (virtual-controller era): manually note in SPIKE-NOTES that ghost entries may appear in Settings > Devices; the upgrade cleanup path is Phase 4 / INST-06 territory, not a Phase 1 regression. Recommended: test on a machine where MicMap has never been installed, or "Forget" any pre-existing MicMap device in Settings > Devices first.
3. Start tailing `vrserver.txt`: `powershell -c "Get-Content -Path '$env:LOCALAPPDATA\Steam\logs\vrserver.txt' -Wait -Tail 5"` (or equivalent).
4. Launch SteamVR.
5. Observe the log tail. Expect within 5-10 seconds:
   - `MicMap driver initializing (sidecar mode)`
   - `MicMap: HTTP server listening on port <N>`
   - `MicMap driver v<version> built <date> <time> - RunFrame starting` (this is the SVR-10 init line on first RunFrame)
   - `MicMap: awaiting HMD container` OR `MicMap: /input/system/click created (handle=<h>)` — depending on HMD power-up timing.
6. Put on the HMD.
7. If not already logged: expect `MicMap: /input/system/click created (handle=<h>)` within 1-2 seconds.
8. Launch `hmd_button_test.exe`. Observe the window opens; "SteamVR: Connected" appears in the status area.
9. Click **Tap (Press + 150ms + Release)**. Observe:
   - (a) SteamVR dashboard opens in-HMD within ~200ms.
   - (b) No laser beam visible from either controller OR from the HMD origin.
   - (c) Dashboard is usable (hover highlights work on clicks from the REAL controller, if present).
10. Close the dashboard (press controller menu button, OR click Tap again which should close it since `/input/system/click` toggles).
11. Open SteamVR Settings > Devices. Verify: no `MICMAP_CONTROLLER_001` or similar entry. If an entry exists AND this is not an upgrade scenario, FAIL the spike and investigate.

**Phase B — Sleep/wake cycle validation (SVR-04, D-02):**
This is the core of the half-day spike — the gap identified in CONTEXT.md where bey-closer-t1 did not validate Case D.

For each cycle i = 1..5 (minimum; recommend 10 if time permits):
1. In the HMD, confirm the dashboard is closed.
2. Take the HMD off. Place it on a surface such that lighthouse tracking is lost AND the proximity sensor is not engaged.
3. Wait for HMD deactivation: SteamVR typically deactivates the HMD within 10-30 seconds. Watch the log tail. Expect `MicMap: HMD deactivated, handle invalidated`.
4. Wait an additional 20-30 seconds to confirm sustained deactivation.
5. Pick up the HMD. Put it on. Wait for reactivation (lighthouse re-locks, or direct-mode HMD reinitializes).
6. In the log tail, expect `MicMap: /input/system/click created (handle=<new h>)` — NOTE the handle value; it should be DIFFERENT from the pre-deactivation handle (per Assumption A2).
7. Click **Tap** in `hmd_button_test.exe`.
8. Verify: dashboard opens. Record `PASS` for cycle i.
9. Close the dashboard. Repeat.

Pass criterion: **all 5 cycles succeed**. Failure in 1+ cycles triggers escalation per the failure playbook below.

**Phase C — Negative-path observations (SVR-10, Pitfall 11):**
1. While the driver is running with the HMD active, kill the MicMap app (`micmap.exe`) mid-session.
2. Send a press via `hmd_button_test.exe` (which is a separate process with its own driver client). Observe: driver accepts it, enqueues, RunFrame presses the button. 5 seconds later, verify the max-hold watchdog fires: `MicMap: max-hold watchdog fired (no UP received in 5000ms)`. Dashboard releases.
3. Trigger a malformed body: use curl from PowerShell: `curl.exe -X POST "http://127.0.0.1:<port>/button" -d 'not-json'`. Expect HTTP 400 response and no state change.
4. Trigger a missing-field body: `curl.exe -X POST "http://127.0.0.1:<port>/button" -d '{}' -H "Content-Type: application/json"`. Expect HTTP 400 response.

**Phase D — Write-up:**
Fill in `01-05-SPIKE-NOTES.md` with the template below. Commit the file.

### Spike Failure Playbook

| Failure Mode | Signal | Next Action |
|--------------|--------|-------------|
| Dashboard doesn't open on Tap (Phase A step 9) | No dashboard visible in HMD | Check log for `UpdateBooleanComponent` error. If `VRInputError_InvalidHandle`: Pitfall 1 regression — handle wasn't actually valid. If `VRInputError_WrongType`: the component path was rejected — SteamVR-version regression (Pitfall 13 / A6). Escalate. |
| Laser beam visible | Visual | Check Settings > Devices for a MICMAP entry. If present: SVR-01 regression — grep driver source for `TrackedDeviceAdded` (should be zero). If absent: upstream SteamVR UI bug — document and confirm with bey-closer-t1 reference implementation on the same hardware. |
| Phase B cycle fails (first post-wake Tap doesn't open dashboard) | Log shows `HMD deactivated` but NO matching re-create log | `VREvent_TrackedDeviceDeactivated` did NOT arrive. D-01 polling fallback is supposed to cover this. Check: is `state_ != Ready` inspected in RunFrame every tick? The three-state enum design should recreate on any non-Ready state. If polling also didn't kick in: deeper investigation needed — likely the handle value IS NOT actually invalid (OpenVR silent churn). Extend RunFrame to always re-check `TrackedDeviceToPropertyContainer` on a timer regardless of state, and retry. |
| Phase B cycle fails repeatedly (2+ out of 5) | Consistent failure on wake | Likely Assumption A2 falsified: CreateBooleanComponent does NOT produce a fresh usable handle after deactivation. Options: (a) Add a per-cycle cleanup step (call UpdateBooleanComponent(false) on the old handle before invalidating — best-effort; may return an error that we ignore). (b) Force a Cleanup+Init cycle on deactivation (heavier, but matches what SteamVR itself does internally for driver reload). Escalate to user decision — this is a research spike's purpose. |
| Max-hold watchdog does not fire in Phase C | Log shows no watchdog line after 5s | `isPressed_` flag handling bug. Review RunFrame step 5 logic in DeviceProvider — specifically the guard that checks `isPressed_ && now - pressTimestamp_ > kMaxHold`. Fix in a hotfix plan 01-06 if needed. |
| 400 responses not returned | Phase C step 3/4 | Handler's try/catch block is not catching. Verify `nlohmann::json::exception` is the base class caught. Possibly the exception name differs between nlohmann versions — use the base `std::exception` as a safety net if needed. |

If the spike passes all phases: SVR-04 and SVR-11 are checked off; Phase 1 is ready for `/gsd-verify-work`.

If the spike fails: DO NOT mark Phase 1 complete. Record findings in SPIKE-NOTES, then either (a) file a hotfix plan 01-06 to address the specific failure, or (b) escalate to the user if the failure indicates a research assumption violation that needs a strategic decision (e.g. Pitfall 13 — SteamVR no longer propagates cross-driver `/input/system/click` updates).
